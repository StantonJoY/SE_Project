## 0. 本文件回答什么

课程方法学（note 行 470）：

> **把共享同一架构 concern 的需求聚类；用该 concern（而非 requirement ID）命名 cluster；
> 每个 cluster 映射到一个独立架构职责；给 cluster 排优先级。**

**为什么必须聚类**：不聚类就会犯两种错（note 行 481–482）——

| 失败模式 | 后果 | 本项目最易犯的地方 |
|---|---|---|
| **Missing a cluster** | 整个架构 concern 被遗忘 | **Evidence（证据）簇**——现在只有一个字段清单，没有监控、没有评估门、没有 hook |
| **Mixing unrelated requirements** | 不兼容的 tactic 被混为一谈 | **确定性强制**需要 wrapper，**降级**需要 timeout + fallback，**两者结构完全不同，不能共用一套设计** |

> 最常见的做法错误：把"超时处理"塞进 compliance 管道里。那会把 fail-closed 的强制层与可用性层耦合，
> 于是**为了可用性而放松强制**——这正是权威崩塌的起点。

## 1. 五个 Concern Cluster

命名规则：**用 concern 命名，不用需求 ID**。

### C1 · Deterministic Authority & Compliance（确定性权威与合规）

**这是核心簇。** 回答的问题是：**AI 说完之后，谁有权否决它？**

| 项 | 内容 |
|---|---|
| **Concern** | AI 的输出必须被确定性代码约束；权威不在模型 |
| **覆盖 ASR** | `ASR-ADS-04`（零逃逸·核心）、`ASR-ADS-05`（敏感品类）、`ASR-ADS-06`（违禁词）、`ASR-ADS-07`（场景约束双层）、`ASR-ADS-12`（注入中和） |
| **覆盖不变量** | `INV-ADS-001`、`005`、`007`、`008` |
| **覆盖需求** | `REQ-ADS-NFR-SAFETY-001`~`004`、`REQ-ADS-SEC-001` |
| **独立架构职责** | **权威边界**：位于 AI 之后的确定性强制层，**五步**纯函数管道，任一失败即 REJECT |
| **实现锚点** | `src/compliance/pipeline.py`（`run_compliance` 及**五个** check 函数）、`src/compliance/rules.py`、`src/ads/banned_words.py` |
| **优先级** | **1（最高）** |
| **现状** | ✅ 已实现（含 6 项 banned_check 状态反例测试） |

**为什么它是独立的职责**：它有自己的一组 **forbidden actions**——compliance 不许被任何路径绕过、不许修改状态、不许改变决策之外的东西。而且它是唯一可以产出"展示/不展示"这一最终裁决的元素。

---

### C2 · Input Contract & Data Integrity（输入契约与数据完整性）

回答：**什么东西有资格进入这个系统？**

| 项 | 内容 |
|---|---|
| **Concern** | 进入系统的数据必须完全符合契约，否则不进 |
| **覆盖 ASR** | `ASR-ADS-01`（素材契约） |
| **覆盖不变量** | `INV-ADS-015` |
| **覆盖需求** | `REQ-ADS-ARCH-001`、`REQ-ADS-FR-001`、`REQ-ADS-FR-002` |
| **独立架构职责** | **准入闸门**：加载期整批 fail-closed + 场景输入校验（非法不进 LLM） |
| **实现锚点** | `src/ads/schema.py`、`src/ads/repository.py`、`src/scene/schema.py`、`src/scene/parser.py` |
| **优先级** | **5（最低，但不可省）** |
| **现状** | ✅ 已实现 |

**降级为什么是"启动失败"而不是"运行期降级"**：素材是**启动期契约**——脏数据一旦进来，
后面每一层都要为它做防御性判断。所以在门口就拒绝，比在每个房间装监控便宜得多。

---

### C3 · Closed-Set Selection & Context Assembly（闭集选择与上下文装配）

回答：**AI 看到什么、能说什么？**

| 项 | 内容 |
|---|---|
| **Concern** | AI 只能在给定候选集内选择，且其上下文（看到什么）必须被架构控制 |
| **覆盖 ASR** | `ASR-ADS-02`（闭集）、`ASR-ADS-03`（输出 schema）、`ASR-ADS-14`（token 预算）、`ASR-ADS-A3-01`（上下文装配）、`ASR-ADS-A3-02`（解释路径隔离） |
| **覆盖不变量** | `INV-ADS-002`、`003`、`004`、`014` |
| **覆盖需求** | `REQ-ADS-ARCH-002`、`003`、`REQ-ADS-NFR-COST-001`、`REQ-ADS-AI-001` |
| **独立架构职责** | **建议层**：候选集构造 → 六层上下文装配 → 闭集选择 → 严格 JSON 解析 → 解释路径（独立） |
| **实现锚点** | `src/selector/`（**P4 待建**） |
| **优先级** | **4** |
| **现状** | ❌ 未实现 |

**这是唯一含 AI 的簇**，也是权威级别最低的簇——它的全部产出都是 advisory。

**为什么它与 C1 必须分开**：C3 的 tactic 是"约束输入、约束输出格式、控制上下文预算"；
C1 的 tactic 是"事后确定性否决"。**一个管"说什么"，一个管"算不算数"。** 混在一起会让人误以为
把 prompt 写严一点就等于合规了——课程明确反对：**安全关键规则绝不写在 prompt 里**（note 行 1310）。

### C4 · Evidence & Traceability（证据与可追溯性）

回答：**事后凭什么证明我干得对？**

| 项 | 内容 |
|---|---|
| **Concern** | 每次决策必须留下完整、可重放的证据；架构缺口不得静默 patch |
| **覆盖 ASR** | `ASR-ADS-10`（审计证据）、`ASR-ADS-13`（权限 + hook）、`ASR-ADS-15`（评估门）、`ASR-ADS-16`（验证完整性·流程）、`ASR-ADS-A3-03`（结构性追溯） |
| **覆盖不变量** | `INV-ADS-009`（流程）、`010`（流程）、`011`（流程）、`012`、`016` |
| **覆盖需求** | `REQ-ADS-GOV-001`、`GOV-002`、`NFR-QA-001`、`NFR-QA-002`、`REQ-ADS-AI-002` |
| **独立架构职责** | **证据层**：审计记录 + 版本溯源 + 评估门 + 权限模型 + pre-commit hook |
| **实现锚点** | `src/audit/`（P6 待建）、`eval/`（待建）、`.opencode/permissions.jsonc`（待建）、pre-commit hook（待建） |
| **优先级** | **3** |
| **现状** | ❌ 未实现（三者全空） |

**⚠️ 这是本项目最容易被遗忘的簇**（对应"Missing a cluster"失败模式）。
现在 `REQ-ADS-GOV-001` 只有一个字段清单：**没有监控项、没有评估门、没有 hook**。
按课程口径，"缺运行时 monitor → 无法发现生产故障"（note 行 5162）——这会直接扣分。

**它包含三条流程不变量**（`INV-ADS-009`/`010`/`011`），而课程标注流程不变量 **Required for full marks**（note 行 5122）。

### C5 · Degradation & Availability（降级与可用性）

回答：**出事了系统怎么退？**

| 项 | 内容 |
|---|---|
| **Concern** | 任何失败都必须有确定、安全、不崩溃的退路 |
| **覆盖 ASR** | `ASR-ADS-08`（低置信度）、`ASR-ADS-09`（fallback 集合）、`ASR-ADS-11`（超时 + 降级 + 监控 + 告警） |
| **覆盖不变量** | `INV-ADS-006`、`013` |
| **覆盖需求** | `REQ-ADS-NFR-SAFETY-005`、`REQ-ADS-FR-003`、`REQ-ADS-NFR-PERF-001` |
| **独立架构职责** | **降级层**：阈值 gate + timeout gate + fallback 路由 + 原因码 + p95 监控 + SLA drift alert |
| **实现锚点** | `src/app/`（P5 待建，编排 + 降级路径） |
| **优先级** | **2** |
| **现状** | ❌ 未实现 |

**优先级为什么这么高**：课程的"性能陷阱"（note 行 590）——
**当违规必须被处理时，延迟阈值就是架构性的**。`REQ-ADS-NFR-PERF-001` 若没有 fallback 路径，
按课程口径"**需求未实现**"。所以这一簇不写，等于需求清单里有一条是假的。

**它与 C1 绝不可混**：C1 是 fail-closed 的**强制层**；C5 是**可用性层**。
若把 timeout 逻辑放进 compliance 管道，迟早会有人为了"别老是没广告"而放松强制。

## 2. 优先级排序

沿用课程 §3.7 的姿态（note 行 528），本项目排序为：

```
Deterministic Authority (C1)                        ← 最高
  > Degradation & Availability (C5)
  > Evidence & Traceability (C4)
  > Closed-Set Selection & Context (C3)
  > Input Contract & Data Integrity (C2)            ← 最低
```

**与课程 VHIS 的差异及理由**（必须显式说明，因为这是判断而非照抄）：

| 位置 | VHIS 排序 | 本项目 | 为什么不同 |
|---|---|---|---|
| 1 | Safety / Invariants | C1 确定性权威 | 一致 |
| 2 | Deterministic Authority | **C5 降级与可用性** | VHIS 有 `REVIEW` 人类兜底，降级不涉及安全声明；本项目 `no_ad` 是**唯一**安全终态，**降级路径本身就是安全主张的一部分**，因此必须紧跟 C1 |
| 3 | Explanation Quality | **C4 证据与可追溯** | 本项目把 Explanation 并进 C3；而 C4 含流程不变量与评估门，分数权重更高 |
| 4 | Cost / Performance | C3 选择与上下文 | 一致（成本并入 C3） |

> **注意一个反常之处，需你确认**：在这个排序里，**"推荐质量"不是优先项**。
> 系统宁愿"不出广告"也不出"可能不合适的广告"。这是 ADR-001 的直接后果，
> 也意味着 C3（唯一含 AI 的簇）优先级**低于**治理类簇。
> 如果团队认为推荐质量应当优先，那要动的是 ADR-001 的准则打分，不是本表。

## 3. 冲突与裁决（课程 §3.7，note 行 530–538）

**隐式或冲突的优先级会鼓励 AI 不一致地猜测**。以下 6 组冲突必须显式裁决：

| # | 冲突 | 裁决 | 依据 |
|---|---|---|---|
| 1 | 语义灵活性 vs 确定性安全 | **确定性代码在权威层面获胜；AI 只在解释层面获胜** | `INV-ADS-001`；ADR-001 |
| 2 | 解释丰富度 vs 严格输出 schema | **解释路径独立**，其格式由独立评估器治理；解释失败不影响决策 | `INV-ADS-004` |
| 3 | Token 预算 vs 上下文完整 | 在 **85% 预算**处触发 compaction；**压缩后重新注入关键约束** | `INV-ADS-014`；`RP-010` |
| 4 | 自动化吞吐 vs 合规零逃逸 | **合规不可协商**；宁可 `no_ad` 也不承担逃逸风险 | `INV-ADS-001`；ADR-002 D1 |
| 5 | 成本优化 vs 审计完整 | **审计不可协商**（`REQ-ADS-GOV-001` 零容忍）；审计写入失败即整体失败 | 课程行 538；ADR-002 D2 |
| 6 | 推荐质量 vs 可用性 | **质量让位于安全，但不让位于可用性**：`no_ad` 是合法终态，**不得**为提升出广告率而放松任何 gate | ADR-002 D1；重开触发 T-1 |

> 第 6 条是本项目特有的。VHIS 没有这一条，因为它不靠"不出广告"来保安全。

## 4. 假设显式化（课程 §3.8，note 行 540–547）

**未言明的假设会变成隐藏缺陷。** 以下假设若不成立，对应簇的设计要改。

| ID | 假设 | 若不成立的影响 | 缓解 + 复审触发 |
|---|---|---|---|
| `A-01` | **"解释"在广告推荐里有可定义的口径** | C3 的解释部分无法验收，退化为装饰性输出 | ✅ **已确认**：「为什么选这条广告」（`OQ-009` 于 2026-10-06 关闭）；触发：解释评估器产不出稳定分数 |
| `A-02` | **`no_ad` 是可接受终态** | C1/C5 的地基要动（需备选降级链或人工队列） | ADR-002 D1；触发：无广告率超阈值（重开 T-1） |
| `A-03` | confidence 阈值 0.5 能有效区分可信/不可信 | C5 的阈值 gate 形同虚设 | ✅ **已定案** = 0.5（`OQ-004` 于 2026-10-06 关闭）；触发：降级率异常则重开 |
| `A-04` | **候选集规模不会超出上下文预算**（当前仅 8 条素材） | C3 的预算裁剪会让 AI 看不到部分候选，选择质量下降 | 素材扩到 30~50 条（OQ-003）时**必须重测**；触发：候选数超预算 |
| `A-05` | 审计写入失败是可以接受的整体失败 | C4 会让服务在存储故障时完全不可用 | ADR-002 D2；触发：失败率超阈值（重开 T-3） |
| `A-06` | 场景特征是**无状态单轮**输入 | C3 的上下文第 4 层（历史）由"不适用"变为适用，compaction 策略要重设 | `scope.out` 已声明不做多轮；触发：引入多轮（重开 T-4） |
| `A-07` | 素材全部本地、量小，可整批驻内存 | C2 的"整批 fail-closed"策略不成立 | 素材为自造 JSON；触发：素材来源改为外部 |

## 5. 簇 → 架构候选的准备

课程 Step 2（P74–76）要求由 cluster 生成 **2–3 个不同的架构候选（A/B/C）**，不是只做一个。
本文件给出候选的**生成轴**：每个候选必须对这五个簇的**职责归属**给出不同答案。

| 候选 | 对 C1 的答案 | 对 C3 的答案 | 对 C5 的答案 | 预期准则表现 |
|---|---|---|---|---|
| **A — Raw**（AI 直接决定） | 无独立强制层（规则写在 prompt） | AI 自由生成文案 | 失败即抛错 | C1 Invariant protection = **Weak**；**应被永久否决** |
| **B — Guarded Hybrid**（ADR-001 选定） | 确定性管道位于 AI 之后 | 闭集选择 + 严格 schema | `no_ad` 单一路径 | C1/C2 Strong；C3 最简 → **选定** |
| **C — Orchestrated**（多 Agent + 人工复核） | 多重复核 + 人工终审 | AI 建议 + 评审路由 | `REVIEW` 队列 + checkpoint | C1 Strong 但 **C3 Complexity = Weak**；**推迟** |

> 上述 A/B/C 与 `adr-001-guarded-hybrid.md` §3–§4 的评价准则打分一致。
> 更完整的候选评价表（10 维准则 + W/M/S 打分）属课程 Step 3 产物 `eval-table.md`，本文件只给生成轴。
