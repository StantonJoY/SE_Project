# Risk List — 假设、可能变成的缺陷与复核触发点（D2.10，optional）

> **状态**：Draft（团队可自由增删）
> **课程对应**：D2 第 10 件 `[optional]` —— *assumptions that could become defects, with review triggers.*
> **编写原则**：**只登记已经或可能真实发生的事**。每一条都能指到本仓库的具体文件、
> 具体 `BUG-` / `TD-` 编号，或具体实测结果。没有凭空想象的假想风险。

---

## 0. 怎么读这张表

| 列 | 含义 |
|---|---|
| **假设** | 系统当前**默认成立但不曾被显式验证**的前提 |
| **若假设失效 → 缺陷** | 不是"可能出问题"，而是"会以什么形态坏掉" |
| **触发条件** | 什么变化会让假设失效 |
| **复核时机** | 什么时候该回来看这一条（**可操作的事件**，不是"定期"） |
| **现状** | 已发生 / 未发生 / 已缓解 |

**排列顺序**：先放**已经真实发生过**的（它们是最高价值的风险证据），再放尚未发生的。

## 1. 已真实发生过的假设失效（本项目的实际教训）

这几条不是预测，是**已经发生过的**。列在这里是因为它们揭示了系统当前仍然依赖的同类假设。

### R-01 `audit/` 目录名在 `.gitignore` 里只匹配根目录

| 项 | 内容 |
|---|---|
| **假设** | `.gitignore` 中不带前导 `/` 的路径模式只影响仓库根 |
| **实际** | gitignore 规则**匹配任意层级**，`audit/` 把 `src/audit/` 一并忽略 |
| **失效后果** | **`src/audit/` 的 3 个文件从未进入仓库**，任何人 clone 后 `import audit` 立刻失败；7 个架构元素缺 1 |
| **触发条件** | 新增目录名与 `src/` 下子模块同名 |
| **复核时机** | 每次新增 `.gitignore` 路径模式、或新增 `src/` 子目录时 |
| **现状** | ✅ 已修复，改为根锚定；记录见 `docs/bug-diary.md` **BUG-008** |

> **它揭示的通用假设**：*「配置文件的匹配语义符合直觉」*。这类假设一旦不成立就是**静默失败**——
> 没有任何门禁会报警，因为文件就是不存在。

### R-02 测试断言与数据文件条数强耦合

| 项 | 内容 |
|---|---|
| **假设** | 素材库固定 8 条 |
| **实际** | `test_ads.py` 硬编码断言 `8` |
| **失效后果** | 数据文件加一条素材，无关功能的测试立刻红 |
| **触发条件** | 修改 `data/ads.json` 的条目数 |
| **复核时机** | 每次扩素材库时 |
| **现状** | ✅ 已修复；记录见 `docs/bug-diary.md` **BUG-005** |

> **通用假设**：*「测试断言反映行为而非数据快照」*。

### R-03 依赖库的默认行为稳定

| 项 | 内容 |
|---|---|
| **假设** | 三个加载器（违禁词表 / 场景规则 / 素材库）的 fail-closed 姿态一致 |
| **实际** | `BannedWords.load()` 与另外两个不同，失败时姿态漂移 |
| **失效后果** | 失败时可能 fail-open——**安全边界在高负载下静默打开** |
| **触发条件** | 新增加载器而不参照既有范式 |
| **复核时机** | 每次新增任何 `load()` / `parse()` 入口时 |
| **现状** | ✅ BUG-007 的具体漂移已修；但**契约统一的不变量仍未立**，`TD-014` 状态为 `open`（处置 `RW-06`，`invariants.md` 属 HUMAN ONLY） |

### R-04 违禁词命中顺序无关

| 项 | 内容 |
|---|---|
| **假设** | 违禁词匹配结果与词表文件顺序无关 |
| **实际** | 结果依赖文件顺序，同一输入不同顺序得到不同命中集合 |
| **失效后果** | 不可重现的合规判定 |
| **触发条件** | 编辑词表文件的行序 |
| **现状** | ✅ 已修复；见 **BUG-006** |

### R-05 沙箱允许子进程创建临时目录

| 项 | 内容 |
|---|---|
| **假设** | `pytest` 的 `tmp_path` fixture 可用 |
| **实际** | 受限沙箱下 5 个测试报 `PermissionError` |
| **失效后果** | 测试在真实 CI 环境与本地表现不一致 |
| **处置** | 测试改用 I/O 边界打桩；`AGENTS.md` ⑥ 第 9 条明令**禁止使用 `tmp_path`** |
| **现状** | ✅ 已规避；见 **BUG-001** |

### R-06 pytest 的 rootdir 与工作目录一致

| 项 | 内容 |
|---|---|
| **假设** | 在仓库根运行 `pytest`，`sys.path` 含仓库根，`from scripts.xxx import ...` 可用 |
| **实际** | **CI 上的 pytest 未把仓库根注入 `sys.path`**，`test/offline/test_corpus.py:50` 抛 `ModuleNotFoundError: No module named 'scripts'`，收集期中断（exit 2），Gate 5 红 |
| **失效后果** | **所有 PR 无法合并**（Gate 5 是 required check） |
| **触发条件** | 工作目录 ≠ pytest 认定的 rootdir；或 pytest / setuptools 版本变化 |
| **复核时机** | 升级 pytest、改 CI 工作目录、或新增任何跨 `scripts/` 的测试 import 时 |
| **现状** | ✅ **已修复（2026-11-24）**。`PR #10` 把 `pyproject.toml` 的 `where = ["src"]` 改为 `where = ["src", "."]` 并加 `exclude` 六项，`scripts` 随 editable 安装注册进 finder，**7/7 全绿** |
| **决定性对照** | 同时段 `PR #7`（只改 `README.md`、不碰 `pyproject.toml`）的 Gate 5 **仍为 failure**。CI 环境相同、单变量差异，故转绿归因于该改动 |
| **当时验证过但确实无效的修法** | ①新增 `scripts/__init__.py`（非仓库根目录下仍报 `ModuleNotFoundError`）；②自定义 build-backend 生成 console script 垫片（13 条门禁命令全绿，Gate 5 收集期仍中断）；③改 `test/offline/test_corpus.py` 的 import 写法（属改既有测试，需 TA，未采用） |
| **曾经误判的修法** | `where = ["src", "."]` 一度被本地实验判为「无效」——**该判断已推翻**。本地只测了"安装后能否 import"，没在 `pip install -e` 之后从非仓库根重跑 pytest。改判全过程见 `option-ledger.md` `O-05` 与 `evaluation-logbook.md` `E-09` |

> **这条是本项目最有价值的一次「判错了又改回来」的记录**：没有对照组时，
> 局部实验会把一个**有效**的修复方案误判为无效。`PR #7` vs `PR #10` 的同环境
> 单变量对照才是决定性证据。教训写进 `O-05` 的「教训」栏。

## 2. 尚未发生、但架构当前依赖的假设

### R-09 LLM 输出永远落在闭集内

| 项 | 内容 |
|---|---|
| **假设** | 模型只会从给定候选里选 |
| **若失效** | 模型返回不存在的 `ad_id` / 非 JSON / 越界字段 |
| **缓解（已实现）** | 严格 JSON gate + schema 校验 → 失败重试 1 次 → 否则 `no_ad`（`INV-ADS-003`、`RP-004`） |
| **触发条件** | 更换模型、更换 provider、修改 prompt 版本 |
| **复核时机** | **每次模型或 prompt 变更**（这也是门禁 4 存在的原因） |

### R-10 评估集能代表真实分布

| 项 | 内容 |
|---|---|
| **假设** | 57 条固定评估用例覆盖真实场景 |
| **若失效** | 门禁 4 全绿但线上质量不达标——**判据本身失效** |
| **缓解** | `ADR-003` 定义分母分离与违规零容忍；`acceptance-coverage-map.yaml` 登记覆盖去向 |
| **触发条件** | 场景分布变化；新增品类 |
| **复核时机** | 每次新增评估用例或修改判据时（改判据须 ADR，`P-009`） |
| **残留** | 登记为 `TD-` 评估债类别（见 `debt-register.md` 的 `evaluation debt` 分类） |

### R-11 预算状态的持久性

| 项 | 内容 |
|---|---|
| **假设** | SQLite 账本跨请求持久，`pay_as_bid` 的历史花费可追溯 |
| **若失效** | 数据库被重置 → 历史花费证据消失；按 `seed()` 重建会**伪造预算** |
| **缓解** | `Ledger.seed/finalize/close` 同事务提交；重复 `request_id` 返回保存响应不重扣费 |
| **触发条件** | 更换数据库、修改 `seed()` 语义、清理 `logs/bidding-v2.sqlite3` |
| **复核时机** | 任何触碰 `src/bidding/ledger.py` 的变更 |
| **注意** | `AGENTS.md` 明文：**预算是跨请求持久状态，不能每次 seed 重置** |

### R-12 Windows 环境下文本文件行尾

| 项 | 内容 |
|---|---|
| **假设** | 仓库内文件统一 LF |
| **若失效** | 在 Windows 上编辑产出 CRLF → **整文件 diff 污染**，评审无法阅读；且 `manifest` 哈希失配（V3 复核发现的 **F-001**） |
| **缓解** | ⚠️ **CI 没有专门的行尾检查**——`F-001` 是 V3 人工复核时偶然发现的，不是门禁拦下的。现行做法：编辑时用 bytes 级归一（`bytes.replace(b"\r\n", b"\n")`），提交前看 `git diff --stat` 是否出现"全文件变更" |
| **触发条件** | 任何人在 Windows 上用带自动行尾转换的编辑器编辑仓库文件 |
| **复核时机** | 每次提交前看 `git diff --stat` 是否出现"全文件变更" |

## 3. 使用方式

- **新增一条**：当你在会话里说"应该没事吧"的时候，就是该写一条的时候。
- **关闭一条**：不是删掉，而是把"现状"改成 ✅ 并写清修复方式与 BUG/TD 编号。
  **已修复的风险仍然有价值**——它证明你曾经想过并处理过。
- **与 `debt-register.md` 的分工**：
  - `risk-list` 记的是**假设**（"我们默认 X 成立"）
  - `debt-register` 记的是**已知欠账**（"我们知道 Y 没做"）
  - 一条风险失效后，往往会变成一条技术债。
