# 场景化广告推荐引擎 — V2 候选需求：报价竞价框架

> 状态：迭代候选 · 2026-09-28
> 定位：在 V1（无 RAG、无竞价）基础上引入**基础报价竞价框架**，需求先行整理。
> 核心变化：LLM 决策层在 V2 中降级为**相关性建议（advisory）**，最终成交、花费、胜负全部由**确定性竞价引擎**计算——安全边界进一步做实。
> 硬性数学校验：竞价模块天然产生一批"零容忍"不变式，是课程 Invariant 注册表、失败测试和评估 replay 的最佳素材。

---

## 1. V2 决策流程（示意）

```
场景特征输入（时段 / 设备 / 用户标签）
        ↓
① 规则预筛（确定性）：场景硬约束 → 候选集
        ↓
② LLM 相关性建议（AI 组件）：为候选集内每条广告打相关性分（只建议，不定成交）
        ↓
③ 竞价引擎（确定性 · 硬性数学校验）：
     校验报价字段 → 过滤预算耗尽广告 → 计算 final_score = f(relevance, bid)
     → 按规则选最高分 → 确定成交价 → 入账 spend
        ↓
④ 合规过滤（确定性 · 安全边界）：违禁词 / 品类禁忌 / 场景限制 / schema
        ↓
⑤ 渲染输出 + 审计日志（含 bid / budget / score / spend 快照）
```

关键设计：**LLM 只提供相关性分数（建议），成交价、花费、胜负都由确定性数学代码决定**——"AI 是顾问，代码是执行官"在 V2 体现到极致。

## 2. 数据模型新增（每条广告）

| 字段 | 类型 | 说明 |
|---|---|---|
| `bid_amount` | 整数（单位：分） | 出价：单次展示愿意支付的最高价 |
| `bid_floor` / `bid_ceiling` | 整数（分） | 出价合法区间（素材级或品类级） |
| `budget_total` | 整数（分） | 总预算 |
| `budget_spent` | 整数（分） | 已消耗（运行时状态） |
| `budget_remaining` | 整数（分） | = `budget_total − budget_spent` |
| `status` | enum | `active / paused / exhausted` |

> 金额一律用**整数分**表示，禁止浮点累计，杜绝精度误差。

## 3. 需求条目（REQ-021 起，延续 V1 编号）

| ID | 类型 | 需求 | 优先级(V2) | 机器可检查的验收标准（Fit Criterion） |
|---|---|---|---|---|
| REQ-021 | Invariant | 出价必须为有限正整数且在合法区间 | Must | 全量素材 `bid ∈ [bid_floor, bid_ceiling]` 通过率 100%；加载期拒绝非法值并报错 |
| REQ-022 | Invariant | 预算不变式恒成立 | Must | 任意时刻 `0 ≤ spent ≤ total` 且 `remaining = total − spent` 精确成立（整数运算） |
| REQ-023 | Invariant | 预算耗尽的广告不得被选中展示 | Must | 被展示广告 `budget_remaining > 0`（或 ≥ 最低可成交额），违规数 = 0 |
| REQ-024 | Invariant | 花费入账精确 | Must | 每次展示后 `spent` 增加恰好等于成交价；全量 `spent` 总和 = Σ 各次成交价（重放核对一致） |
| REQ-025 | Invariant | 金额计算使用整数分，禁止浮点累计 | Must | 全量金额字段为整数类型，累计过程零精度丢失（代码审查 + 属性测试） |
| REQ-026 | Invariant | 评分计算为确定性纯函数 | Must | 相同输入重复计算得分逐位一致；评估集 replay 零差异 |
| REQ-027 | Invariant | 数值异常（NaN/Inf/溢出）必须拦截 | Must | 注入异常数值样本 100% 被拒绝并走降级，不进入决策 |
| REQ-028 | Invariant | 成交价规则唯一且确定 | Must | 成交价按唯一指定规则（pay-as-bid 或次价，二选一）计算，实现唯一、文档明确 |
| REQ-029 | Invariant | 平局必须有确定性 tie-break | Must | 分数相同时按固定规则（如 `ad_id` 升序）胜出，输出不允许随机 |
| REQ-030 | Functional | 竞价引擎在候选集内按最终分数选胜者 | Must | 胜者 = 分数最高且预算充足者；分数公式单一来源、可配置 |
| REQ-031 | Functional | 最终分数公式明确 | Must | `final_score` 公式（如 `relevance × bid` 或加权）在配置中单一来源；变更必须触发评估 replay |
| REQ-032 | Functional | LLM 仅提供相关性建议，不直接决定成交 | Must | LLM 输出 schema 不含成交价/花费字段；上述字段由竞价引擎写入（schema 层强制） |
| REQ-033 | Functional | 预算耗尽自动转 `exhausted` 并退出候选 | Must | 展示后 `remaining = 0` 的广告下一轮不再进入候选集 |
| REQ-034 | Functional | 竞价格局审计快照 | Must | 每次决策日志含 `bid / budget / spend / final_score / 成交价`，可完整重放决策过程 |
| REQ-035 | Quality | 竞价模块全部离线可测 | Must | 竞价引擎为纯逻辑模块（无 LLM 依赖），`test/offline` 全覆盖 |
| REQ-036 | Security | 报价数据防篡改/防注入 | Should | 素材加载期 schema + 范围双重校验；异常报价样本 100% 拒绝 |
| REQ-037 | Governance | 竞价规则变更须经评估 replay + 架构决策 | Must | 语义评估 gate 覆盖竞价变更；AI-use 日志同步；涉及安全关键路径需人工批准 |
| REQ-038 | Quality | 评估集扩展报价场景 | Should | 新增用例：预算耗尽、出价越界、平局、数值异常、花费重放，合计 ≥ 10 条 |
| REQ-039 | Performance | 竞价计算开销可忽略 | Should | 100 条候选内单次竞价计算耗时 < 50ms（离线基准） |

## 4. 硬性数学校验要点（给不变式/测试的抓手）

- **三条算术恒等式**：`remaining = total − spent`；`spent 增量 = 成交价`；`Σspent = Σ成交价`
- **两个区间约束**：`bid ∈ [floor, ceiling]`；`spent ∈ [0, total]`
- **两类非法数值**：非有限数（NaN/Inf）、溢出 → 一律拒绝
- **一个确定性要求**：同输入同输出，平局有固定规则，禁止随机/浮点抖动
- **一个权限边界**：LLM 无成交/花费写权限，schema 层强制

## 5. 待讨论

- [ ] 成交价规则：pay-as-bid（付自己的出价）还是次价（Vickrey，付第二高出价）？V2 建议 pay-as-bid 最简
- [ ] 最终分数公式：`relevance × bid` 是否够？要不要加权（场景匹配度 × 相关性 × bid）？
- [ ] 预算粒度：总预算够吗？要不要加日预算 / 频控（单用户曝光上限）？
- [ ] LLM 相关性分的尺度：0~1 连续值 vs 离散 1~5？尺度影响与 bid 相乘的权重
- [ ] 报价数据来源：自造素材时人工设定，需不需要模拟真实分布（如正态出价）？
- [ ] 与 V3（RAG）的关系：竞价先于 RAG 落地？两者正交，可独立迭代
