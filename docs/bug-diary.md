## BUG-001 · 测试依赖宿主临时目录，在受限沙箱下 5 个测试报 `PermissionError`

| 字段 | 内容 |
|---|---|
| **症状** | 运行 `pytest test/offline` 得到 `59 passed, 5 errors`。5 个 error 全部来自 `test_ads.py` 中使用了 `tmp_path` fixture 的用例，报 `PermissionError: [WinError 5] 拒绝访问` |
| **复现** | 1. 在受限沙箱会话中运行全量离线测试；2. 观察 5 个 `tmp_path` 用例以 error（非 failure）终止；3. 错误发生在 pytest 的 `tmpdir.py::getbasetemp` → `make_numbered_dir`，即**收集临时目录阶段**，测试函数体从未执行 |
| **分类** | **测试环境耦合缺陷**（非产品代码缺陷）——测试隐式依赖"宿主允许在系统临时目录创建目录"这一未声明前提 |
| **根因** | 两级原因：<br>① **直接原因**：pytest 的 `tmp_path` 在 `C:\Users\...\Temp\dsh-*\pytest-of-<user>` 下创建编号目录，该路径对受限沙箱子进程不可写。<br>② **深层原因**：架构缺少一条不变量——**"测试必须对环境无副作用依赖"**。当时的测试策略只规定了"确定性、不调 LLM"，未规定"不依赖文件系统可写性"。 |
| **修复** | 把 5 个用例从"写临时文件再读取"改为**在文件 I/O 边界打桩**：<br>• 新增 `_FakePath` 类，在 `p.exists()` 边界返回测试指定的真值（用于"文件不存在"用例，**永不触碰磁盘**）；<br>• 新增 `_fake_read()` 辅助，用 `monkeypatch.setattr(builtins, "open", ...)` 返回 `io.StringIO`（用于坏 JSON / 重复 ID / 缺字段 / 非法枚举用例）；<br>• 结果为 `66 passed`，**0 error**。<br>同时把"测试不得使用 `tmp_path`"写入 `verification-constraints.md` §5 作为项目约束。 |
| **暴露的缺口** | **新增不变量候选**：测试与宿主环境解耦（当前登记为 `verification-constraints.md` §5 的**流程约束**，尚未提升为 `INV` 条目）。<br>另暴露：原先的 `59 passed, 5 errors` 曾被误读为"环境限制、与我无关"——**"可归因于环境"是掩盖缺陷的常见借口**。正确做法是改造测试使其不依赖该环境。 |

## BUG-002 · 需求注册表 schema 的条件约束结构性错误，`asr_id` 被错误地设为全局必填

| 字段 | 内容 |
|---|---|
| **症状** | 校验器报 5 项 `[schema] baseline_requirements/N: 'asr_id' is a required property`，其中 4 条需求**根本没有声明 `asr: true`** |
| **复现** | 1. 在 `req-schema.json` 中把 `allOf` 嵌套写在 `if/then` 的 `then` 分支内部；2. 运行 `scripts/validate_requirements.py`；3. 观察 `asr_id` 对所有需求都成为必填 |
| **分类** | **治理工件缺陷——schema 逻辑错误**（不是数据错误；数据是对的，规则写错了） |
| **根因** | JSON Schema 里 `allOf` 是**同级的 applicator 关键字**，不能作为 `then` 的值来嵌套条件。我写成了：<br>`{"if": {...}, "then": {"allOf": [{"if":..., "then":...}, ...]}}`<br>导致内层 `if` 失去与正确父级的关联，`required: ["asr_id"]` 被无条件应用。 |
| **修复** | 拆成两个**同级** `allOf` 条目：<br>① 只放 `description` 说明规则；<br>② 条件为 `asr == true` **且** 不含 `deferred_to_round`，`then` 要求 `asr_id`。<br>另为"一条需求强制多个 ASR"增加 `asr_ids` 数组，并把条件改为"存在 `asr_ids` 时不必填 `asr_id`"。 |
| **暴露的缺口** | **无对应不变量**——治理工件（schema 本身）没有验证约束。当前由 `validate_requirements.py` 的出口码 + 35 个注册表测试间接保护，但**schema 内部逻辑的正确性没有独立检查**。<br>候选动作：为 `req-schema.json` 增加"用已知会失败的样本验证 schema 会拒绝"的自测（部分已由 `test_requirements_registry.py` 的负向测试覆盖）。 |

## BUG-003 · 校验器漏检"孤儿 ASR"，根因是一条需求可强制多个 ASR

| 字段 | 内容 |
|---|---|
| **症状** | `ASR-ADS-A3-01`（Token Budget）在 `asr-register.md` 中登记，但被报为"未被任何需求引用（孤儿 ASR）"；同一校验轮次还报 `REQ-ADS-ARCH-001`"不变式类 ASR 未登记任何 INV 条目" |

| **暴露的缺口** | **跨工件一致性本身需要不变量保障**。当前由 `validate_requirements.py` 第 3 层强制（注册表 ↔ ASR 登记册 ↔ 不变量登记册**双向**校验，孤儿即 FAIL）。<br>这条机制已被 `test_requirements_registry.py::test_orphan_asr_rejected` 与 `test_unknown_asr_id_rejected` 覆盖。 |

| 字段 | 内容 |

## BUG-006 · 违禁词命中非确定性：结果依赖词表文件顺序

| 字段 | 内容 |
|---|---|
| **症状** | 同一段文本，在词表顺序不同时命中的违禁词**不同**。实测三组全部复现：<br>• 30 字文本 → 原序 `'赌博'` / 逆序 `'返现'`<br>• 18 字文本 → 原序 `'高利贷'` / 逆序 `'内部价'`<br>• 12 字文本 → 原序 `'兼职刷单'` / 逆序 `'祖传秘方'` |
| **复现** | 1. `BannedWords(list(words)).check(text)`；2. `BannedWords(list(reversed(words))).check(text)`；3. 两者返回值不同。词表有 **15 个 2 字词、6 个 3 字词、3 个 4 字词**，等长命中普遍存在 |
| **分类** | **确定性缺陷**（违背 `REQ-ADS-ARCH-004`：确定性部分同输入必须逐位一致）。同时是**证据缺陷**——拒绝理由归因不稳定 |
| **根因** | `check()` 用 `max(hits, key=len)`。`max` 在**等长**时返回**迭代序中先出现者**，而迭代序来自 `_words` 元组，即 JSON 文件的书写顺序。原实现假设"最长命中唯一"，但数据里有大量等长词，假设不成立 |
| **修复** | 改为两级规则并写进文档：<br>① **最长优先**（`longest = max(len(w) for w in hits)`）——更具体的命中更有诊断价值；<br>② **长度相同时取 Unicode 码点最小者**（`min(w for w in hits if len(w) == longest)`）——与顺序无关。<br>补 `test_banned_words.py`：等长顺序无关性、码点序规则、最长优先、真实词表逆序一致、以及 **24 种词表排列**下命中唯一 |
| **修复中的自我纠正** | 我第一次改成了 `max(hits, key=lambda w: (len(w), w))`，但文档写的是"码点**最小**"——`max` 取的是**最大**，实现与文档矛盾。直接验算才定案（`max`→返回 `返现`，`min`→返回 `博彩`）。**教训：涉及排序的断言必须打印实际值验算，不能靠推理。** |
| **暴露的缺口** | 新增候选不变量：**过滤器的判定结果不得依赖配置文件的书写顺序**。已写入 `banned_words.py` 的模块 docstring，并由测试锁定。<br>另暴露：`invariants.md` 的 `INV-ADS-007` 原只写"含违禁词的广告绝不被展示"，**未覆盖"命中归因必须确定"**——归因不确定会影响审计可复现性。 |

## BUG-007 · `BannedWords.load()` 的 fail-closed 姿态与其他加载器不一致

| 字段 | 内容 |
|---|---|
| **症状** | 三个加载器的错误行为各不相同：`AdRepository.load` → `AdLoadError`（含文件存在性预检）；`SceneRules.load` → `SceneRulesLoadError`（含存在性预检）；`BannedWords.load` → **原始 `FileNotFoundError` / `JSONDecodeError` / `ValueError`**，无存在性预检 |
| **复现** | 1. 对三者分别传入不存在的路径；2. 观察异常类型：前两者为专属异常，第三者透传文件系统异常；3. 再传入 `{"words": [...]}`（顶层非数组）→ 第三者抛泛型 `ValueError` |
| **分类** | **fail-closed 一致性缺陷**。所有入口**确实都拒绝**了（都是 fail-closed），但**契约不一致**：调用方无法用统一方式捕获"加载失败"，且错误来源（文件系统 vs 数据格式）无法区分 |
| **根因** | `BannedWords` 是三个加载器里**唯一没有专属异常类型**的。原实现把"文件不存在"交给 `open()` 自然抛出，把"格式错误"交给泛型 `ValueError` |
| **修复** | 新增 `BannedWordsLoadError`，与另两者的命名和语义对齐；补齐：文件存在性预检、非法 JSON、顶层非数组、元素非字符串、**空词表**（空表 = 合规过滤形同虚设 → 必须拒绝启动）。另加 `__init__` 的顶层 `isinstance(words, list)` 检查（原先传 dict 会静默迭代其键） |
| **覆盖缺口（顺带发现）** | `BannedWords` 原先**完全没有专属测试文件**——`test_ads.py` 只有 3 个正向用例（命中/未命中/check_all），**零个负向测试**。这意味着这个安全关键加载器此前没有反例保护。已补 `test_banned_words.py`（13 个测试，含 6 个负向） |
| **暴露的缺口** | **新增候选不变量：所有 safety-critical 数据加载器必须使用专属异常类型且共享同一 fail-closed 姿态。** 当前 `AdLoadError` / `BannedWordsLoadError` / `SceneRulesLoadError` 满足，但**没有一条不变量或结构约束强制这一点**——新增加载器时可能再次漂移。已登记为 `TD-014`。 |

## 2. 同类审计发现（尚未修复，需决策或补数据）

> 以下 4 项由 `scripts/audit_implementation.py` 系统发现，**不是代码逻辑错误**，而是
> **强制的可达性/覆盖缺口**——代码里的分支从未被真实数据处理过。

| ID | 发现 | 性质 |
|---|---|---|
| `AF-001` | 规则 `category_blacklist` 含 `'medical'`，但素材库**无该品类** → 规则永久空转 | 死规则（数据缺口） |
| `AF-002` | 规则级 `night_blocked_categories`（夜间禁 gaming）**不可达**：唯一的 gaming 素材 `ad_003` 已声明 `not_night`，预筛先拦下 → **两层防护完全重叠** | 冗余 + 规则级分支零行使 |
| `AF-003` | 规则级 `campus_blocked_categories`（校园禁 adult）**不可达**：唯一的 adult 素材 `ad_006` 已声明 `not_campus` → 同上 | 冗余 + 规则级分支零行使 |
| `AF-004` | 字段 `banned_check`（`checked`/`banned`/`pending`）在 schema 与 models 中声明、8 条素材全填 `checked`，但 **compliance 层从不读取它** → 标为 `'banned'` 的素材仍会被展示 | 声明了却不强制 |

**`AF-002`/`AF-003` 的意义**：架构文档把"预筛 + 终检"称为**双层防护**，但实测**两层完全重叠**——
规则级那一层从未被行使过。这**不是漏洞**（冗余防护不会漏拦），但意味着那条规则级分支**缺独立验证**。
补一条"未声明素材级限制的同类素材"即可让两层解耦并分别验证。

**`AF-004` 的语义后果最需要注意**：`banned_check: "banned"` 是**声明式标注**，读起来像"这条已被标记为禁投"，
但实际没有任何代码据此拦截。**声明与强制之间的落差是审计中最容易被误读的地方。**

## 3. 汇总与本轮教训

| Bug | 分类 | 状态 | 暴露的缺口类型 |
|---|---|---|---|
| `BUG-001` | 测试环境耦合 | ✅ 已修（80 passed） | 流程约束（待提升为不变量） |
| `BUG-002` | schema 逻辑错误 | ✅ 已修 | 治理工件缺独立验证 |
| `BUG-003` | 数据模型表达力不足 | ✅ 已修 | 跨工件一致性校验（已强制） |
| `BUG-004` | 格式混淆 | ✅ 已修 | 工件机器可读性即防线 |
| `BUG-005` | 测试脆弱性 | ⚠️ **已知未修** | 测试与数据解耦 |
| `BUG-006` | **确定性缺陷** | ✅ **已修**（+5 测试） | 判定结果不得依赖配置书写顺序 |
| `BUG-007` | **fail-closed 不一致** | ✅ **已修**（+6 测试） | 加载器契约统一（`TD-014`） |
| `AF-001~004` | 可达性/覆盖缺口 | ⚠️ **待决策/补数据** | 声明 ≠ 强制；冗余防护掩盖未验证分支 |

**本轮（2026-10-06 代码审计）三条教训**：

1. **"可归因于环境"是掩盖缺陷的常见借口**（`BUG-001`）。真正的问题不是沙箱，而是测试隐式依赖了未声明的前提。
2. **治理工件本身也会写错，且没有测试保护**（`BUG-002`、`BUG-003`、`BUG-004` 都是工件缺陷，不是产品缺陷）。
   因此**工件必须被机器读取**——一旦被脚本消费，格式与逻辑错误会在下一次校验时立刻暴露。
3. **涉及排序/比较的代码，必须打印实际值验算，不能靠推理**（`BUG-006` 的自我纠正）。
   我连续两次把中文码点序推错（把 `max` 当成取最小）。**推理正确 ≠ 事实正确。**
4. **"声明了却不强制"是最危险的落差**（`AF-004`）：`banned_check: "banned"` 读起来像已生效的保护，
   实际零强制。审计时必须区分"字段被存取"与"字段参与判定"。
